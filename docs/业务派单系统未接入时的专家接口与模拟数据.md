# 业务派单系统未接入时的专家接口与模拟数据

## 1. 实现目标

课题一负责专家档案、认证、状态、常规可服务时间、临时不可用、任务级利益冲突核验结果和画像。当前还提供一条最小可联调的接单与正式安排确认链路，用于在正式派单系统未接入时验证后半段流程。需求受理、推荐排序和派单决策仍不属于课题一。

当前没有派单系统，因此本次不建设简化派单系统，而是提供以下能力：

1. 稳定接口：未来业务系统通过固定接口查询专家资格并提交业务证据。
2. 适配层：当前读取模拟或人工导入的业务快照，未来替换为真实派单系统适配器。
3. 明确三态：`ELIGIBLE`、`INELIGIBLE`、`REQUIRES_MANUAL_CONFIRMATION`。
4. 后半段闭环：业务发起接单，专家接受并确认冲突，业务确认正式安排后生成占用快照；取消时释放占用。
5. 模拟数据隔离：所有模拟记录带 `MOCK` 标记，不参与正式统计。

核心原则：常规时间表有空，不代表专家实际没有被派单。没有业务快照时必须返回 `UNKNOWN` 或需要人工确认，不能返回实际空闲信息。

另一个关键原则：专家接受任务不等于正式派单。必须同时满足 `status=ACCEPTED` 和 `arrangement_status=CONFIRMED`，才表示正式安排已成立。

## 2. 接口清单

### 2.1 查询授权专家摘要

```http
GET /expert/open/v1/experts/{userId}/snapshot
```

权限：

```text
expert:open:query
```

返回专家基本档案、认证状态、接单状态、画像版本和常规服务时间。不返回手机号、邮箱和实际任务占用。

### 2.2 核验专家是否能进入后续业务

```http
POST /expert/open/v1/eligibility
```

权限：

```text
expert:open:query
```

请求示例：

```json
{
  "userId": 12,
  "externalTaskId": "TASK-2027-001",
  "taskType": "TECH_INSURANCE_REVIEW",
  "serviceStart": "2027-01-13 09:00:00",
  "serviceEnd": "2027-01-13 12:00:00",
  "serviceMode": "REMOTE",
  "serviceRegion": "江苏省南京市",
  "industry": "新能源"
}
```

返回结果包含：

- `decision`：最终核验结论。
- `checks`：逐项检查结果。
- `reasons`：不通过或需要人工确认的原因。
- `businessContext`：业务快照中的占用、冲突、来源和核验时间。
- `candidateRanked=false`：课题一不进行候选排序。

返回示例：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {
    "decision": "REQUIRES_MANUAL_CONFIRMATION",
    "manualConfirmationRequired": true,
    "candidateRanked": false,
    "checks": [
      {
        "code": "BUSINESS_OCCUPANCY",
        "status": "WARN",
        "message": "系统暂时无法确认这段时间是否已有安排，请人工核实"
      }
    ],
    "businessContext": {
      "occupancyStatus": "UNKNOWN",
      "conflictStatus": "UNKNOWN",
      "source": "MOCK_OR_MANUAL_SNAPSHOT",
      "verifiedAt": null,
      "taskRefs": []
    }
  }
}
```

`decision` 的三种取值：

| 取值 | 含义 | 业务系统处置 |
|---|---|---|
| `ELIGIBLE` | 专家域硬门禁通过，业务快照明确显示无占用、无冲突 | 可进入后续派单流程 |
| `INELIGIBLE` | 认证、状态、时间或冲突明确不满足 | 不得进入后续派单流程 |
| `REQUIRES_MANUAL_CONFIRMATION` | 认证和时间满足，但实际占用或任务级冲突尚不清楚 | 人工确认后继续 |

### 2.3 接单与正式安排

业务工作台接口：

```http
POST /expert/business/task-acceptance-requests
GET  /expert/business/experts/{userId}/task-acceptances
POST /expert/business/task-acceptances/{confirmationId}/confirm-arrangement
POST /expert/business/task-acceptances/{confirmationId}/cancel-arrangement
```

专家端接口：

```http
GET  /expert/workspace/task-acceptances
POST /expert/workspace/task-acceptances/{confirmationId}/respond
```

课题二集成接口：

```http
POST /expert/open/v1/task-acceptance-requests
POST /expert/open/v1/task-acceptances/{confirmationId}/confirm-arrangement
POST /expert/open/v1/task-acceptances/{confirmationId}/cancel-arrangement
```

状态模型：

```text
status              PENDING / ACCEPTED / REJECTED
arrangement_status  NOT_CONFIRMED / CONFIRMED / CANCELLED
```

专家提交接单结果时，同时提交：

```json
{
  "acceptanceStatus": "ACCEPTED",
  "conflictStatus": "NONE",
  "statement": "已核对任务参与方，本次无利益冲突。",
  "version": 0
}
```

约束：

- 业务人员必须先主动完成当前任务的资格核验，页面才允许发起专家接单。
- 切换到其他任务后必须重新核验，不能复用上一个任务的核验结论。
- 后端在创建接单请求前会再次执行最新核验，`INELIGIBLE` 请求会被拒绝。
- `PENDING` 记录才能由专家提交接单结果。
- `ACCEPTED + CONFIRMED` 冲突组合被拒绝。
- 只有 `status=ACCEPTED` 且任务冲突不是 `CONFIRMED` 时，业务才能确认正式安排。
- 确认正式安排会写入 `OCCUPIED` 快照。
- 取消正式安排会把同来源的正式安排快照更新为 `FREE`。
- 已取消记录不能直接恢复为确认；标准演示可重新执行清洁测试脚本，正式环境应使用新的任务版本或任务号，避免覆盖历史审计记录。

## 3. 接收服务报告、评价和信用事实

```http
POST /expert/open/v1/service-evidence
```

权限：

```text
expert:open:evidence:write
```

请求示例：

```json
{
  "sourceEventId": "EVENT-2027-001",
  "userId": 12,
  "evidenceType": "SERVICE_REPORT",
  "externalTaskId": "TASK-2027-001",
  "sourceSystem": "mock-dispatch",
  "sourceKind": "MOCK",
  "occurredAt": "2027-01-14 10:00:00",
  "title": "科技保险专家服务报告",
  "summary": "服务按期完成，报告结构完整。",
  "rawPayload": "{\"reportQuality\":\"GOOD\"}"
}
```

支持的证据类型：

- `SERVICE_REPORT`
- `EVALUATION`
- `CREDIT`

支持的来源类型：

- `EXTERNAL`
- `MANUAL_IMPORT`
- `MOCK`

接口特性：

- `sourceEventId` 唯一，重复提交返回已有记录并标记 `duplicate=true`。
- 自动计算原始载荷的 SHA-256 摘要。
- 证据状态保存为 `RECEIVED`。
- 本接口不会自动更新专家画像。后续仍需由 Agent 生成建议，并经过人工审核。

## 4. 数据库表

### 4.1 `expert_business_context_snapshot`

业务上下文只读快照，用于保存外部派单系统或联调流程提供的占用和任务级冲突结果。标准接单流程中，原始 `FREE` 基线来自模拟导入；业务确认正式安排后，系统新增一条 `source_kind=EXTERNAL` 的 `OCCUPIED` 快照。

关键字段：

| 字段 | 用途 |
|---|---|
| `expert_user_id` | 专家用户ID |
| `external_task_id` | 外部任务号 |
| `service_start`、`service_end` | 快照覆盖的时间段 |
| `occupancy_status` | `FREE`、`OCCUPIED`、`BLOCKED` |
| `conflict_status` | `NONE`、`POTENTIAL`、`CONFIRMED`、`UNKNOWN` |
| `source_system` | 来源系统 |
| `source_kind` | `EXTERNAL`、`MANUAL_IMPORT`、`MOCK` |
| `source_version` | 来源版本和幂等键 |
| `verified_at` | 业务源核验时间 |

### 4.2 `expert_service_evidence`

外部服务报告、评价和信用事实的接收表。该表只保存业务证据，不代表课题一已经生成或批准了画像更新。

## 5. 执行数据库脚本

先执行结构、权限和角色迁移：

```powershell
mysql -u root -p science_expert < backend/sql/migrations/20261119_expert_open_api_mock.sql
mysql -u root -p science_expert < backend/sql/migrations/20261119_expert_formal_arrangement.sql
```

再执行模拟数据：

```powershell
mysql -u root -p science_expert < backend/sql/seeds/20261119_expert_open_api_mock_data.sql
```

模拟数据脚本会自动选择前两个满足以下条件的专家：

```sql
review_status = 'APPROVED'
service_status = 'AVAILABLE'
del_flag = '0'
```

脚本会读取该专家第一条有效常规时间表，为前两位专家各生成一条：

- 下一个对应星期：与常规时间表完全一致，`FREE`、`NONE`。

默认不再生成 `OCCUPIED` 用例。需要验证占用时，应单独准备一条业务占用快照。

这样可以避免出现“业务快照有空，但专家常规时间表不覆盖”的无效演示数据。执行后使用下面的 SQL 查看实际日期：

```sql
SELECT expert_user_id, occupancy_status, service_mode,
       service_start, service_end
FROM expert_business_context_snapshot
WHERE source_kind = 'MOCK'
ORDER BY service_start;
```

同时生成一条 `MOCK` 服务报告证据。

当前默认数据覆盖：

```text
专家 106：一条 FREE / NONE
专家 107（expert2）：一条 FREE / NONE
```

`expert2` 的常规时间为星期二 09:00—15:15：

```text
2026-11-24 09:00—15:15  FREE / NONE
```

检查模拟数据：

```sql
SELECT p.user_id, p.real_name, s.*
FROM expert_profile p
JOIN expert_business_context_snapshot s
  ON s.expert_user_id = p.user_id
WHERE s.source_kind = 'MOCK'
ORDER BY s.verified_at DESC;

SELECT evidence_id, source_event_id, expert_user_id, evidence_type,
       source_kind, processing_status
FROM expert_service_evidence
WHERE source_kind = 'MOCK';
```

如果数据库中不存在已认证且正常接单的专家，模拟业务快照不会插入。此时应先完善专家档案、认证和可服务时间。

## 8. 联调步骤

1. 登录系统并获取 Token。
2. 查询具有模拟数据的专家。
3. 根据模拟快照日期和专家常规时间表调用 `/eligibility`。
4. 使用上一步查询出的实际日期和时间，分别验证以下场景：

```text
FREE 快照日期与时间 -> ELIGIBLE
OCCUPIED 快照日期与时间 -> INELIGIBLE
业务快照没有覆盖的时间 -> REQUIRES_MANUAL_CONFIRMATION
```

5. 调用 `/service-evidence` 提交模拟报告，再重复提交相同 `sourceEventId`，确认返回 `duplicate=true`。

curl 示例：

```powershell
curl.exe -X POST "http://127.0.0.1:8080/expert/open/v1/eligibility" `
  -H "Authorization: Bearer <TOKEN>" `
  -H "Content-Type: application/json" `
  -d "{\"userId\":<专家ID>,\"externalTaskId\":\"TASK-DEMO-001\",\"serviceStart\":\"<FREE快照开始时间>\",\"serviceEnd\":\"<FREE快照结束时间>\",\"serviceMode\":\"<快照服务方式>\"}"
```

## 10. 后续接入真实派单系统

保持 `ExpertOpenApiController` 和 `ExpertOpenApiService` 的对外契约不变，新增真实适配器：

```text
HttpBusinessContextAdapter
```

由真实派单系统提供以下事实：

- 专家在指定时间段是否已被任务占用。
- 任务级利益冲突是否已经核验。
- 来源系统、核验时间和版本。

将 `BusinessContextPort` 的实现从模拟快照切换到真实适配器即可。专家认证、状态、时间声明、画像和审核逻辑无需修改。

## 11. 当前限制

1. 当前证据接口只完成接收和审计，不自动生成画像更新建议。
2. 利益冲突结果是任务级业务事实，不能仅由专家档案推断。
3. 接口不提供候选推荐、排序、任务创建、任务占用写入和派单。
4. `MOCK` 和 `MANUAL_IMPORT` 数据只能用于开发和联调，正式部署前必须接入真实业务源或保留人工确认。

- 最新已发布审核版本中的能力画像。
- 常规服务时间和每周承接上限。
- 已审核通过的利益冲突说明。
- 利益冲突与独立性相关画像维度。
- 针对具体任务时间段的服务方式、区域、产业、占用和冲突核验结果。

## 14. 服务证据驱动画像更新

### 14.1 处理链路

```text
外部服务报告/评价/信用事实
  -> 证据接口校验并保存
  -> 生成结构化画像更新建议
  -> 管理员修改批准分值或驳回
  -> 批准后生成新的画像审核版本
```

证据接收接口：

```http
POST /expert/open/v1/service-evidence
```

接收成功后：

- 证据状态从 `RECEIVED` 更新为 `SUGGESTED`。
- 系统根据证据类型和正负向文本信号生成待审核建议。
- 建议包含维度、当前分、建议分、理由、证据和置信度。
- 生成建议阶段不修改当前生效画像。

### 14.2 审核接口

```http
GET  /expert/admin/profile-updates
GET  /expert/admin/profile-updates/{suggestionId}
POST /expert/admin/profile-updates/{suggestionId}/review
```

审核权限：

```text
expert:profile-update:review
```

批准请求示例：

```json
{
  "action": "APPROVE",
  "version": 0,
  "comment": "证据有效，批准更新",
  "items": [
    {
      "itemId": 1,
      "approvedScore": 82
    }
  ]
}
```

驳回请求必须填写 `comment`。驳回后不生成画像版本。

批准后：

- 将人工确认分值合并进最新画像快照。
- 生成新的 `expert_release_version`。
- 提升专家画像版本号。
- 保存审核人、意见和建议版本。
- 将证据状态更新为 `APPLIED`。

驳回后：

- 将建议标记为 `REJECTED`。
- 将证据状态更新为 `REJECTED`。
- 当前生效画像保持不变。

### 14.3 页面

```text
专家管理 -> 画像更新审核
```

页面可以查看证据摘要和逐维度建议；批准前可以修改每个维度的最终分值。

### 14.5 当前实现说明

当前更新建议优先调用 DeepSeek 画像分析 Agent。Agent 接收当前专家档案、30维画像、本次实时服务证据和最近服务证据，生成带维度、建议分、理由、证据和置信度的结构化建议。

生成记录通过 `generation_mode` 区分：

```text
AGENT          DeepSeek Agent 实时分析
RULE_FALLBACK  Agent 未配置或调用失败时使用规则基线
SEEDED         早期模拟脚本导入
```

每条建议同时保存 `prompt_version`、`model_name` 和 `agent_output_json`，便于审计。无论自动生成方式是什么，都必须经过管理员审核；批准后才生成新的生效画像版本。

## 15. 任务占用、风险预警和专家接单

### 15.1 任务占用只读台账

业务经办人员可以通过：

```http
GET /expert/business/experts/{userId}/occupancy
```

查询指定时间段的外部任务占用快照。业务工作台新增“任务占用”页签，展示：

- 外部任务号
- 占用时间
- FREE/OCCUPIED/BLOCKED
- 冲突状态
- 服务方式
- 来源系统和来源版本

该数据只读，课题一不创建任务或修改占用。

### 15.2 风险预警审核

新增数据表和页面：

```text
expert_risk_review
专家管理 -> 风险预警审核
```

外部风险事件接口：

```http
POST /expert/open/v1/risk-events
```

服务报告/评价证据中出现投诉、低评价或信用负向信号时，系统也会自动生成风险预警。

审核动作：

```text
ACKNOWLEDGE  确认并记录
DISMISS      忽略并说明理由
```

风险预警不会自动删除档案、退出专家或修改接单状态。如需暂停、限制或退出，仍按专家状态审核流程处理。

### 15.3 专家接单与任务级利益冲突确认

业务经办人员可以针对具体任务发起确认：

```http
POST /expert/business/task-acceptance-requests
POST /expert/open/v1/task-acceptance-requests
```

专家端新增：

```text
专家接单
```

专家首先确认是否接受任务：

```text
ACCEPTED    接受任务
REJECTED    拒绝任务
```

同时确认本次任务利益冲突：

```text
NONE        无冲突
POTENTIAL   存在潜在冲突
CONFIRMED   存在明确冲突
```

资格核验会合并外部快照冲突和专家任务级确认结果：

| 冲突状态 | 资格结果 |
|---|---|
| `CONFIRMED` | `INELIGIBLE` |
| `POTENTIAL` 或待确认 | `REQUIRES_MANUAL_CONFIRMATION` |
| 任务确认 `NONE` | 可继续其他硬门禁检查 |

存在明确冲突时不能直接接受任务。任务级确认只影响当前外部任务，不修改长期利益冲突声明或常规服务时间。

### 15.4 标准专家接单测试用例

执行：

```powershell
mysql -u root -p science_expert < backend/sql/seeds/20261119_expert_acceptance_clean_test.sql
```

该脚本会清理现有接单测试记录和旧接单占用快照，只生成业务任务占用快照，不预置接单请求：

```text
任务号：TEST-EXPERT-ACCEPTANCE-001
专家：106
时间：2026-12-07 07:30—09:30
方式：REMOTE
区域：江西省
产业：人工智能
业务占用：FREE
业务冲突：NONE
接单状态：尚未发起
```

业务人员填写上述任务信息并点击“发起专家接单”后，专家端才会看到该请求。专家接受任务并确认无冲突后，业务人员再点击“确认正式安排”。此时系统生成该任务的 `OCCUPIED` 快照。

使用同一任务号和时间核验时，预期：

```text
decision = ELIGIBLE
TASK_ACCEPTANCE = PASS
BUSINESS_OCCUPANCY = PASS
TASK_CONFLICT = PASS
```

脚本同时准备了同一专家、同一时间段的对照任务 `TEST-EXPERT-ACCEPTANCE-002`。在 `TEST-EXPERT-ACCEPTANCE-001` 确认正式安排后，使用 002 的相同时间核验，预期：

```text
decision = INELIGIBLE
BUSINESS_OCCUPANCY = FAIL
taskRefs 包含 TEST-EXPERT-ACCEPTANCE-001
```

原因是适配器会忽略当前任务自己的 `OCCUPIED`，但其他任务的同时间段 `OCCUPIED` 仍然是阻断项。

点击“取消正式安排”后：

```text
arrangement_status = CANCELLED
正式安排来源快照 occupancy_status = FREE
```

取消不等于删除接单记录，历史确认说明、确认人和来源版本都要保留供审计。
