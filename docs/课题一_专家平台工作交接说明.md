# 课题一专家平台工作交接说明

## 1. 先明确交接范围

总体需求文档覆盖四个课题：

- 课题一：专家档案、认证、画像、状态、时间声明和利益冲突声明。
- 课题二：需求受理、专家匹配、派单和调度。
- 课题三：报告复核与知识复用。
- 课题四：服务工单、费用、评价和信用处置。

当前代码主要实现课题一，并提供部分面向课题二的专家查询接口，以及一条可联调的“专家接单后由业务确认正式安排”的后半段链路。当前仍没有实现课题二的需求受理、候选排序、自动派单决策和协同调度，也没有实现课题三、课题四的完整业务流程。

交接时必须坚持以下边界：

- 专家接受任务只表示专家接受本次邀约，不等于正式派单。
- 只有业务经办人员确认正式安排后，系统才生成该任务的 `OCCUPIED` 业务快照。
- 课题一不负责需求受理、候选筛选、排序和自动派单决策。
- 课题一不能替课题二决定最终候选或安排。
- 课题一不能替专家库管理员批准专家退出。
- 课题一不能自行生成信用结论或真实服务评价。
- 业务快照只保存外部业务事实，不代表课题一实际执行了派单。

总体需求文档是业务边界依据，本说明是当前代码实现状态和交接注意事项。

## 2. 当前角色和入口

### 2.1 业务经办人员

角色：

```text
role_key = business_operator
role_name = 业务经办人员
```

菜单：

```text
业务专家查询
```

权限只有：

```text
expert:business:view
```

可以查看：

- 已正式认证、未退出的专家有效档案。
- 最新已发布画像。
- 常规服务时间。
- 已审核利益冲突声明。
- 针对具体任务的资格、占用和冲突核验结果。

可以处理：

- 为具体任务发起专家接单请求。
- 在专家接受后确认正式安排。
- 取消已确认的正式安排并释放任务占用。

不可以：

- 编辑专家档案。
- 修改服务时间。
- 审核认证材料。
- 批准画像变更。
- 修改长期服务时间或长期利益冲突声明。
- 调用开放专家接口。

创建业务经办人员账号的方法：

1. 管理员进入“系统管理 -> 用户管理”。
2. 新建普通用户。
3. 只分配“业务经办人员”角色。
4. 不要同时分配专家、审核人员或管理员角色。

### 2.2 管理员画像审核

管理员菜单：

```text
专家管理 -> 画像更新审核
```

权限：

```text
expert:profile-update:review
```

管理员可以修改每个维度的批准分值，也可以驳回建议。批准后才生成新的画像版本。

### 2.3 开放接口账号

面向课题二或外部系统的接口使用：

```text
expert:open:query
expert:open:evidence:write
```

这两个权限不属于只读业务经办人员，应交由受控的系统集成账号或管理员使用。

## 3. 当前接口清单

### 3.1 业务经办人员页面接口

```http
GET  /expert/business/experts
GET  /expert/business/experts/{userId}
POST /expert/business/eligibility
GET  /expert/business/experts/{userId}/task-acceptances
POST /expert/business/task-acceptance-requests
POST /expert/business/task-acceptances/{confirmationId}/confirm-arrangement
POST /expert/business/task-acceptances/{confirmationId}/cancel-arrangement
```

用途：

- 专家检索。
- 有效档案、画像、时间表和冲突信息查看。
- 指定任务时段的资格核验。
- 发起专家接单请求、查看任务接单状态，以及确认或取消正式安排。

`POST /eligibility` 是查询语义，不创建任务，也不修改专家档案。`task-acceptance-requests` 只创建专家接单确认请求，不代表已经派单。

### 3.2 开放专家接口

```http
GET  /expert/open/v1/experts/{userId}/snapshot
POST /expert/open/v1/experts/snapshots
POST /expert/open/v1/eligibility
POST /expert/open/v1/service-evidence
POST /expert/open/v1/task-acceptance-requests
POST /expert/open/v1/task-acceptances/{confirmationId}/confirm-arrangement
POST /expert/open/v1/task-acceptances/{confirmationId}/cancel-arrangement
```

接口用途：

| 接口 | 用途 |
|---|---|
| 单专家快照 | 获取课题二所需的完整专家事实 |
| 批量专家快照 | 一次查询最多 100 位专家 |
| 资格核验 | 核验认证、状态、时间、占用和冲突 |
| 服务证据接收 | 接收服务报告、评价和信用事实 |
| 发起接单请求 | 课题二把已经确定要邀约的专家和任务送入平台 |
| 确认正式安排 | 课题二或业务工作台确认任务后生成占用快照 |
| 取消正式安排 | 释放该正式安排产生的占用 |

批量快照返回档案、画像、标签、常规时间、临时不可用和冲突声明。它明确返回：

```json
{
  "matchingDecision": false,
  "dispatchDecision": false
}
```

课题二仍负责候选排序、安排计算、人工确认、邀约和派单。

### 3.3 画像更新审核接口

```http
GET  /expert/admin/profile-updates
GET  /expert/admin/profile-updates/{suggestionId}
POST /expert/admin/profile-updates/{suggestionId}/review
```

处理链路：

```text
服务证据 -> 画像更新建议 -> 人工审核
-> 批准生成新画像版本 / 驳回保持当前画像
```

当前建议生成优先调用 DeepSeek 画像分析 Agent，读取当前专家档案、30维画像、本次实时服务证据及最近服务事实，生成结构化更新建议。

Agent 未配置或调用失败时，系统使用规则基线降级。建议通过 `generation_mode` 区分：

```text
AGENT
RULE_FALLBACK
SEEDED
```

管理员审核和版本生成流程已经闭环。

前两条来自通用模拟脚本，重跑时会根据当前日期和专家常规时间表计算下一个对应星期，日期可能变化。`TEST-EXPERT-ACCEPTANCE-001` 当前固定为 `2026-12-07 07:30—09:30`；如需用于其他日期，应同步修改标准测试脚本、页面选择的任务时间以及验收文档。

当 `TEST-EXPERT-ACCEPTANCE-001` 完成“专家接受且业务确认正式安排”后，系统会额外生成一条：

```text
expert_user_id = 106
external_task_id = TEST-EXPERT-ACCEPTANCE-001
occupancy_status = OCCUPIED
source_kind = EXTERNAL
source_version = arrangement-{confirmationId}
```

此时该测试任务会有两条快照：一条原始 `FREE` 基线，一条正式安排生成的 `OCCUPIED`。核验本任务时忽略它自己的 `OCCUPIED`；核验其他同时间段任务时，该 `OCCUPIED` 会阻断。

业务工作台的“任务占用”页面会按“任务编号 + 任务开始时间 + 任务结束时间”合并，只展示最新状态。数据库中的原始 `FREE`、后续 `OCCUPIED` 和取消后的 `FREE` 仍全部保留，用于审计和冲突计算。

必须强调：

- 业务快照不是专家时间表。
- 业务快照模拟未来派单系统提供的实际占用和任务级冲突结果。
- 专家时间表表示专家声明的可服务时段。
- 两者都满足才可能返回 `ELIGIBLE`。
- 没有快照时返回 `REQUIRES_MANUAL_CONFIRMATION`，不能解释为空闲。

2. 进入“业务专家查询”。
3. 查询 expert 和 expert2。
4. 打开有效档案、画像、常规时间和利益冲突页签。
5. 确认没有编辑、审核、发布或删除按钮。

### 6.2 expert2 资格核验

使用：

```text
2026-11-24 09:00—15:15，REMOTE
```

预期：

```text
ELIGIBLE
```

使用：

```text
2026-12-01 09:00—15:15，REMOTE
```

预期：

```text
INELIGIBLE
```

使用没有业务快照的其他对应星期二：

```text
REQUIRES_MANUAL_CONFIRMATION
```

### 6.3 批量专家快照

```powershell
curl.exe -X POST "http://127.0.0.1:8080/expert/open/v1/experts/snapshots" `
  -H "Authorization: Bearer <TOKEN>" `
  -H "Content-Type: application/json" `

```

检查：

- `availableForMatching=true`。
- `dimensions` 包含画像维度。
- `schedules` 包含常规时间。
- `matchingDecision=false`。
- `dispatchDecision=false`。

### 6.4 接单与正式安排闭环

状态分为两组，不能混用：

```text
status              PENDING / ACCEPTED / REJECTED
arrangement_status  NOT_CONFIRMED / CONFIRMED / CANCELLED
```

推荐在业务工作台按以下顺序验证：

1. 执行标准接单测试脚本，确认当前没有接单记录。
2. 业务人员在专家 106 的“利益冲突核验”页签选择 `TEST-EXPERT-ACCEPTANCE-001`。
3. 必须先点击“核验当前任务”。未核验、核验结论已过期对应到其他任务，或核验结论为 `INELIGIBLE` 时，接单按钮不可用。
4. 核验不是 `INELIGIBLE` 后，点击“发起专家接单”，业务端显示 `PENDING / NOT_CONFIRMED`。
5. 再用专家 `expert` 登录，在“专家接单”中同时选择“接受接单”和“无冲突”，填写说明并提交。
6. 回到业务端，任务状态应变为 `ACCEPTED / NOT_CONFIRMED`。
7. 点击“确认正式安排”，状态变为 `ACCEPTED / CONFIRMED`，并生成 `OCCUPIED` 快照。
8. 用同一任务号核验，本任务应返回 `ELIGIBLE`；改用另一个任务号和相同时间段核验，应因为业务占用返回 `INELIGIBLE`。
9. 点击“取消正式安排”，状态变为 `ACCEPTED / CANCELLED`，正式安排生成的快照更新为 `FREE`；该记录不能直接恢复为确认。重新验收时执行清洁测试脚本；正式环境应使用新的任务版本或任务号，避免覆盖历史审计记录。

关键接口：

```http
POST /expert/business/task-acceptance-requests
GET  /expert/workspace/task-acceptances
POST /expert/workspace/task-acceptances/{confirmationId}/respond
POST /expert/business/task-acceptances/{confirmationId}/confirm-arrangement
POST /expert/business/task-acceptances/{confirmationId}/cancel-arrangement
```

存在明确冲突 `CONFIRMED` 时不能接受任务，也不能确认正式安排。专家接受任务但业务尚未确认正式安排时，不能作为最终占用事实。后端创建接单请求前会再次执行最新核验，即使绕过页面直接调用接口，`INELIGIBLE` 也会被拒绝。

### 6.5 画像更新闭环

1. 调用 `/service-evidence`，使用新的唯一 `sourceEventId`。
2. 查询“画像更新审核”中的待审核建议。
3. 修改批准分值或填写驳回意见。
4. 批准后检查是否出现新的 `expert_release_version`。
5. 检查专家的 `graph_version` 是否增加。
6. 检查证据状态是否变为 `APPLIED`。

## 7. 接手人最容易误判的地方

1. 不要把常规时间表当成实际任务空闲。
2. 不要把没有业务快照当成没有任务。
3. 不要给业务经办人员开放接口写权限。
4. 不要把课题二的需求受理、匹配、排序和派单继续塞进课题一。
5. 不要让课题一 Agent 直接改写生效档案或画像。
6. 不要把模拟服务报告当作真实评价或信用结论。
7. 不要在生产环境使用 `MOCK` 数据参与统计或排名。
8. 不要认为批量快照接口已经完成匹配和派单决策。
9. 不要把规则基线包装成已完成的 LLM Agent 研究结果。
10. 不要仅凭页面按钮完成判断，必须用数据库中的版本和审核记录验证闭环。
11. 不要把 `status=ACCEPTED` 当成正式派单，正式安排必须看 `arrangement_status=CONFIRMED`。
12. 不要用“当前任务自己的 `OCCUPIED`”阻断本任务；它只用于阻断其他同时间段任务。
